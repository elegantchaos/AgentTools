# 2026-10-07

## Calendar access spike

Sam wants the Agents repository's `baseline:summaries` skill to report upcoming appointments and reminders, through a small bespoke `agt` command in place of a broad calendar integration. A bespoke command limits what reaches the agent, which matters because anyone who can send Sam an invitation can put text in his calendar.

The question that decides the design is which process macOS charges with the privacy permission (TCC). For a command-line tool it is normally the responsible app that launched it: Terminal, or the Claude desktop app. Granting the permission there would give it to every process an agent runs.

Tested with a throwaway app bundle (`com.elegantchaos.agt.calendar-spike`, `LSUIElement`, `NSCalendarsFullAccessUsageDescription`, ad-hoc signed) whose executable prints EventKit's authorization status and, when asked, requests full access and counts today's events. macOS 27.0.1, Swift 6.4.

- Before any request, the Claude desktop app had no calendar access (`notDetermined`).
- Launched with `open -n --stdout <file> <bundle> --args …`, the helper's parent is `launchd`, so it is its own responsible process. `--stdout` returns its output. `open -W` failed ("Unable to block on application"), probably because the helper exits before `open` can wait on it.
- The request prompt named the helper ("CalSpike"), not the Claude app. After Sam allowed it, the helper had `fullAccess` and read today's events.
- The same executable run directly from the agent's shell still reported `notDetermined`: the permission belongs to the bundle launched through LaunchServices, not to the file.
- Rebuilding after a comment-only change produced an identical binary, and the permission held. A real code change produced a new code hash, and the helper was back to `notDetermined`. An ad-hoc signed grant is pinned to the code hash, so a modified helper needs a new prompt. The signing identity is irrelevant under ad-hoc signing; the only signing identity on this machine is Apple Development, and the agent can see it.
- On macOS 14 and later, reading events needs full access; there is no read-only tier. Restrictions on what reaches the agent have to be in the helper's own code.

The public `open` route works, so the private responsibility-disclaim spawn attribute is not needed.

Open:

- Whether Mint 0.18 links a second executable product. 3.8.0 has one, so the installed `~/.mint/bin` shows only `agt`.
- Getting completion from `open` without `-W`, for example by reading a named pipe passed as `--stdout` until end of file.
- Reminders use a separate permission (`NSRemindersFullAccessUsageDescription`); not yet tried.

Sam can remove the spike's permission in System Settings → Privacy & Security → Calendars.

### Follow-up: one binary

- Sam chose to put calendar access in `agt` itself, not a separate helper. A helper does not narrow the exposure: any process running as Sam can launch whichever bundle holds the permission and read what it returns. The protection is the bundle's limited output, and one binary keeps that visible. Sam accepts approving a new prompt after each `agt` update.
- `agt` runs other tools, and its children inherit the permission, so when it runs from the calendar bundle it must accept only calendar queries.
- `NSWorkspace.openApplication(at:configuration:)` launched the bundle with `launchd` as parent and returned its process identifier, which a `kqueue` `NOTE_EXIT` wait can use to learn when it finishes, with results written to a file passed as an argument. That launch ran a rebuilt executable, so it reported `notDetermined`; the attribution under `NSWorkspace` is still to be confirmed with the real `authorize` command.

### Follow-up: one executable, with private API

- Sam prefers a single `agt` executable with no app bundle, and accepts private API, since `agt` will never go through App Store review.
- Spiked a bare executable with an Info.plist embedded by `-Xlinker -sectcreate -Xlinker __TEXT -Xlinker __info_plist`. It relaunches itself with `posix_spawn` after `responsibility_spawnattrs_setdisclaim(&attributes, 1)`, found with `dlsym`. `responsibility_get_pid_responsible_for_pid` reports the responsible process.
- Run directly, the responsible process was the Claude desktop app. The disclaimed child was responsible for itself, and its standard output reached the parent through the inherited descriptors.
- The request prompt named the tool ("agtspike 2", as Sam read it). After Sam allowed it, the disclaimed child had `fullAccess` on later runs too, while the same binary run directly stayed `notDetermined`.
- The binary kept its linker signature, with the Info.plist not bound, so a plain SwiftPM or Mint build should behave the same.
- Not tested: that processes started by a self-responsible `agt` inherit its permission. That is the documented model, so `agt` must refuse everything except calendar queries whenever it is its own responsible process.

## `agt calendar`

Implemented [0007](../Decisions/0007-calendar-access-runs-in-agt-as-its-own-responsible-process.md), which Sam accepted after the spikes.

- `agt calendar authorize`, `events` and `reminders` (`--days`, 1 to 14). Each relaunches `agt` disclaimed with the same arguments and `AGT_CALENDAR_RELAUNCHED` set; a relaunched process that is still not self-responsible stops instead of relaunching again.
- `AgentToolsLauncher` replaces the direct call to `AgentToolsCommand` in the entry point. When `agt` is its own responsible process it parses with `CalendarOnlyCommand`, whose only subcommand is `calendar`.
- `EventKitCalendarStore` copies only the reported fields out of EventKit. `CalendarReport` passes every stored string through `CalendarText.singleLine`, which collapses whitespace, drops control characters and caps the length at 80, so stored text cannot add output lines or terminal escapes.
- Settings come from `calendar.calendars` and `calendar.reminderLists` in `~/.agt/config.json`, read with swift-configuration like the project configuration.
- The Info.plist is embedded with `-sectcreate` through `unsafeFlags`, with an absolute path from `Context.packageDirectory`.
- Tests cover text reduction, windows, formatting and filtering, access checks with an in-memory store, the execution plan, the calendar-only root, and a disclaimed spawn's exit status. The EventKit store itself is not unit-tested, since it needs the permission.
- Checked by hand with the debug build: `agt calendar events` relaunched itself and the relaunched process reported calendars "not determined" for the new identity. A disclaimed `agt` given `validate --plan`, `refresh` or `sandbox configure` failed to parse them, and accepted `calendar events`.

- With the debug build, `agt calendar authorize` showed two prompts; Sam allowed both. They named the executable file, `agt-debug` (the copy run), not the Info.plist's `CFBundleDisplayName`, so the installed `agt` is named "agt" and a renamed copy shows its own file name. `events --days 2` then listed real events, all-day and timed, with locations and calendar names, and `reminders --days 3` listed incomplete reminders. `--days 15` was rejected.
- Overdue reminders reached back years (the oldest from 2022), which is noise for a daily summary. Sam chose to list only reminders overdue by up to seven days, over listing all of them or summarising older ones as a count. `CalendarQueries.overdueDays` sets the limit, and EventKit's incomplete-reminder predicate now gets a start date. This was not rechecked against real reminders: a rebuilt binary needs a new approval.

Not yet checked: Mint linking the unsafe flags when it builds a release.

## The package test-action bug: cause

Started on `feature/package-test-action`, from the open bug in the [2026-09-30 entry](2026-09-30.md). Fixture packages with a test target, in workspaces built for the purpose, Xcode 27.0:

- `Leaf` alone as a `group:` member: "Scheme Leaf is not currently configured for the test action."
- `Solo` and `Other`, independent members: the same, for both.
- `Top` depending on `Leaf`, both members: the same, for both, including `Top`, which nothing depends on.
- `Leaf` tested in its own directory (`xcodebuild -scheme Leaf test`, no workspace): passed.

So the trigger is neither of the two conditions the 2026-09-30 entry suspected. A package's generated scheme has a test action only when that package is opened directly; inside a workspace it never does. The 2026-09-25 rule that a workspace member is a root, which `ValidationDiscovery.rootPackages` implements, was stated without a recorded check and is wrong for Xcode 27. Only a shared scheme file that lists the package's tests makes a workspace scheme testable.

## Exploring scheme-first full validation

Sam asked whether full validation should always run the product's tests through Xcode, with the scheme or a test plan covering the local packages, instead of testing packages separately.

- A workspace scheme whose default test plan lists package test targets by container (`"containerPath": "container:Leaf"`) ran those packages' tests in one `xcodebuild test`, although the packages' own schemes have no test action. `-showTestPlans` listed the plan and `-testPlan "Full Validation"` selected it.
- A plan target whose package is not a workspace member is skipped without any message, and the run still reports `TEST SUCCEEDED`. A scheme's testables behave the same way. Any scheme-first design needs a coverage check.
- Bookish already validates scheme-first: with every product package excluded, full validation is four steps (build and test the Bookish scheme for macOS and iOS). Timed in a worktree of `main` at `47751967`, with the simulator pre-boot: 203 s cold, 81 s warm. Xcode's test operation took 18.6 s on macOS and 30.5 s on iOS of the warm run. The 2026-09-28 per-package plan, 22 steps, took 8 m 56 s cold and 4 m 44 s warm without pre-boot, and 2 m 25 s with it.
- Each test run executed 524 tests in 18 bundles, covering every product package and the Application, Commands, Icons and Logger submodules.
- The comparison found a gap: the `KeychainTests` and `SettingsTests` targets of the Keychain and Settings submodules are not in the Bookish scheme, so full validation never runs them (they run only when their submodule changes and is tested on its own). This is the silent loss a coverage check would report.
- `mcpbridge` ships with Xcode 27 as a stdio bridge to a running Xcode's MCP tool service. Its tools were not listed, since connecting asks Sam for approval in Xcode.

## Scheme-first coverage

Sam chose to warn about and separately test packages that the product schemes miss, and to check schemes as well as test plans.

- `SchemeTests` reads a product scheme's tests: its `Full Validation` plan, else its default plan, else its testables, with `container:` paths resolved against the directory of the workspace or project holding the scheme. A fixture with the plan in a `Plans/` folder confirmed plan target paths are relative to that directory, not to the plan: `container:Top` ran, and `container:../Top` found no test bundles.
- Package testables in a scheme have no `BlueprintName`; the target is named by `BuildableName` (Bookish's scheme). Project testables have both.
- `TestCoverage` covers a package when one or more product schemes run every one of its test targets and it is a workspace member. Covered packages get no steps; the others are warned about and tested separately when the submodule policy tests them. Without scheme tests nothing is checked, so per-package projects see no warnings.
- `XcodeSchemes.hasTests` also accepts a `TestPlanReference`; a plan-only scheme previously counted as having no tests, which would have dropped its test step.
- Packages in submodules the policy does not test are now described when the product reaches them, repeatedly until no new package is reached, so the check sees them. Their summaries say "tested by scheme" when a scheme runs them.
- `ValidationDiscovery.rootPackages` became `workspaceMemberPackages` (used for the membership check) and `isOpenedDirectly` (the only case where a generated package scheme can test).
- Checked on Bookish `main` with the exclusions overridden away: four steps, every package "tested by scheme Bookish" except Keychain and Settings, both warned about. Checked on the fixture: validation passed with `-testPlan "Full Validation"` and no package steps.
