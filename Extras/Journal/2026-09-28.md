## Follow-up: sharing build outputs with the IDE

- The separation in decision 0003 protects against build output contention; it is stronger than the core rule that validation must not rewrite source or build inputs. A shared build directory is safe for sequential equivalent builds, but concurrent behavior differs between tools.
- Ran two Xcode 27 builds of the same fixture simultaneously with one fresh DerivedData path. One passed in 11.5 seconds; the other failed in 2.1 seconds with `unable to initialize database (database is locked)`. Xcode detected the collision but did not wait for the first build.
- Ran two SwiftPM 6.4 builds of the same fixture simultaneously with one fresh scratch path. Both passed. One printed `Another instance of SwiftPM is already running ... waiting until that process has finished execution` and finished after the first build.
- Sharing with Xcode's normal DerivedData would therefore need an explicit response to lock contention, such as a bounded retry, and could delay background validation while the IDE builds. SwiftPM's own lock serializes concurrent use of the same scratch path. The working-tree fingerprint already marks a background result stale if tracked or untracked source changes during the run, independent of cache location.
- Do not change decision 0003 without explicit confirmation. If revised, distinguish the nonnegotiable ban on modifying source/build inputs from a configurable choice of build output location, and document collision behavior for background validation.
- Current validation does not pass SwiftPM's `--only-use-versions-from-resolved-file` or Xcode's `-onlyUsePackageVersionsFromResolvedFile`. Both tools advertise those options for preventing automatic resolution to versions absent from `Package.resolved`. The user's clarified rule that validation must not change build inputs needs a separate check of resolution behavior before shared output paths are implemented.
