## PR 3 review: package test coverage

Reviewed `feature/package-test-action` at `87f407b0bdc6b9fa422dd7302d03eda999193a22`, against the PR's base and decision [0008](../Decisions/0008-full-validation-runs-package-tests-through-the-product-scheme.md).

- `SchemeTests` treats an enabled test target as complete coverage even when the plan selects or skips individual tests. A scratch executable compiled from the PR's parser and coverage code reproduced a plan selecting only `CoreTests/testOne()` being reported as full coverage, with no warning. Scheme testables also ignore individual test selection. The coverage model needs to distinguish a full target from a filtered target before removing separate package steps.
- A separately tested package is routed through a shared scheme whenever `hasTests` finds any testable or plan reference. The scheme's effective tests are not compared with the package's complete target list. In particular, a plan-only package scheme newly qualifies even if its default plan omits a package test target; the coverage warning promises separate testing, but the selected scheme still omits that target. Fallback routing needs the same completeness check.

## Follow-up: review fixes

Both findings were correct and are fixed on the branch.

- `TestTarget` records whether it is filtered. A plan entry with a non-empty `selectedTests` or `skippedTests` is filtered; the plan is read as plain JSON, so any form of selection counts. A scheme testable is filtered when it has `useTestSelectionWhitelist = "YES"`, `<SelectedTests>` or `<SkippedTests>`. A filtered target never covers its package; the warning says the scheme "runs only some tests of" it.
- `SchemeTests.runsAllTests(_:in:)` compares a scheme's unfiltered targets with every test target of the package. A separately tested package goes through its shared scheme only when that is true and the package is a workspace member (`ValidationDiscovery.schemeTestsPackage`); otherwise it is tested in its own directory.
- A package scheme's `Full Validation` plan is now passed with `-testPlan` too, so the plan the completeness check read is the plan that runs.
- `resolve` dropped the filter flag when rebuilding a target; the new tests caught it.
- Checked on the fixture: a plan selecting one test of `LeafTests` warned and gave `Leaf` its own step, while `Top` stayed covered. Bookish's scheme selects and skips nothing, so its plan is unchanged.
