## Plan for 2.2

- Validation must never share build directories with an IDE: concurrent builds stall on locks, and differing flags throw away each other's products. It either owns its build directory or hands the build to the IDE.
- SwiftPM: build into a private `--scratch-path` so validation stops fighting VS Code's Swift extension over `.build`.
- Xcode: when Xcode has the workspace open, build and test through Xcode's MCP bridge (`xcrun mcpbridge`) so validation reuses Xcode's own cache, falling back to `xcodebuild` with private DerivedData. Check the tool surface against Apple's documentation first; decide between an MCP client in `agt` (deterministic, preferred) and routing in the `swift:validation` skill.
- VS Code: no known external build/test API in the Swift extension; verify before ruling it out.
- Add fixtures in `Extras/`: a small Xcode project, a small SwiftPM library, possibly a VS Code workspace, for integration tests.
- Carry over the ReleaseTools roadmap item: run subprocesses through `Runner` and set `VALIDATING=1` for `swift` child processes so manifests can detect validation.
- Known limitation: warning detection matches `warning:` anywhere in a line, so test names or output containing that text flag a step as `[warnings]`.
- Known limitation: stdout is block-buffered when piped, so a thrown error's message can appear before earlier step output.

## Validation redesign

Reviewed the design against the goals now in the README. Speed is the first priority, because validation runs after every change.

Findings: validation takes one exclusive path (workspace, else packages, else project), so it never covers the whole product; the fast-then-full sequence lives in the agent, not the tool; packages are only built for the host; Xcode tests are opt-in; format and lint cover only uncommitted files; configuration is per-run flags.

Plan, each step releasable:

1. `agt format [--check]`: format and lint every tracked and untracked Swift file, to bring whole codebases into line. Split from validation, so validation never modifies source.
2. Build hygiene: drop `-DVALIDATING` (its only use is hiding `#Preview` blocks, and `CoreUI` in ActionStatus builds its previews with Swift 6.4's default Swift Build) and the explicit `--build-system swiftbuild` (now the default). Redirect SwiftPM and Xcode caches into one shared `agt` cache directory that agent sandboxes allow once, and keep build products per project. Prove no stray writes with a `sandbox-exec` test over fixtures in `Extras/`. Consider detecting an enclosing sandbox to pass SwiftPM's `--disable-sandbox` automatically.
3. Discovery as its own phase, cached under `.build/agt/` and keyed by a fingerprint of manifests, project files, the validation config, and the `agt` and Xcode versions; `agt validate --plan` shows what would run.
4. Fast phase: map changed files to SwiftPM targets through their source paths, build those targets for the host, and run their tests; fall back to an app scheme on its first supported platform.
5. Full phase in the background: build the live working tree into validation's own build directories (shared with the fast phase, so the full phase starts warm), tag each result with the working tree's hash at the start, and discard the result if the tree changed during the run. Report through `agt validate status` and `wait`; a matching tree hash reuses the last result. Snapshotting the tree into a separate checkout was considered and deferred: it breaks relative dependencies outside the repository, needs recursive submodule snapshots, and omits ignored-but-needed files. Revisit it only if background runs are invalidated too often.

Recorded [0003: validation does not modify the project](../Decisions/0003-validation-does-not-modify-the-project.md).

Held back: routing builds through Xcode's MCP bridge, until the speed of background validation is measured. Parallel phases, since builds already use every core.

Open: platforms cannot be read from package manifests (`platforms:` only sets minimum versions), so the full phase needs a declared platform set per project.

## Step 1: `agt format`

- Added `agt format [--check]` and removed formatting and linting from `agt validate`, per [0003](../Decisions/0003-validation-does-not-modify-the-project.md). It formats all 44 Swift files in this repository in about 0.4 seconds.
- Lint findings are reported without failing, for now. A per-project configuration file or directory (for example `.agt/`) could later choose stricter behaviour per project.
- Files come from `git ls-files` (tracked plus untracked, honouring ignores; submodule contents excluded). Swift files under `Tests/**/Resources` are skipped as fixtures, using the same rule as package discovery. `swift format` has no ignore file, so other files opt out with `// swift-format-ignore-file`.
- Extracted `StepRunner` (logged steps and the summary) and `OutputOptions` so both commands share them. The command echo shows a file count instead of every path.
- Breaking for `agt validate`, so the next release is 3.0.0; the `swift:validation` skill must run `agt format` first.

## Step 2: build hygiene

- Dropped `-DVALIDATING` and `--build-system swiftbuild`. The fixture's `#Preview` builds without them.
- Each Swift package builds into `.build/agt/swiftpm/` (the root package in `root/`, nested packages under `packages/<path>`), so validation never shares `.build` with an IDE. Logs and Xcode products moved under `.build/agt/` too.
- Added `Extras/Fixtures/SwiftPackage` (a library with a `#Preview` and a Swift Testing target) and `Extras/Scripts/sandbox-check.sh`, which runs validation under `sandbox-exec` with writes allowed only where an agent's sandbox should allow them. It is a script, not a unit test, because it runs real builds. The system log did not record the sandbox's denials, so writes a tool attempts and quietly gives up on are not detected; denied writes that matter fail the build.
- Planned a shared `agt` cache directory, then dropped it: `xcodebuild` always writes package manifests to `~/Library/Caches/org.swift.swiftpm` (no flag moves it), and compiles manifests that import `CompilerPluginSupport` with the default clang module cache in `$(getconf DARWIN_USER_CACHE_DIR)clang/ModuleCache` (it ignores `CLANG_MODULE_CACHE_PATH`). Since those locations must be allowed anyway, SwiftPM keeps its standard caches too, which also shares downloads with ordinary builds.
- Nested sandboxes: SwiftPM's and Xcode's own sandboxes (manifests, package plugins, macro plugins, build scripts) cannot start inside an agent's. Validation probes once with `sandbox-exec` (exit 71, `sandbox_apply: Operation not permitted`, when nested) and then passes `--disable-sandbox` to SwiftPM, and `-IDEPackageSupportDisableManifestSandbox=YES`, `-IDEPackageSupportDisablePluginExecutionSandbox=YES`, `SWIFTC_DISABLE_SANDBOX=YES`, and `ENABLE_USER_SCRIPT_SANDBOXING=NO` to `xcodebuild`. `xcodebuild` accepts Xcode defaults only in `-Key=value` form.
- Found and fixed a silent skip: when `xcodebuild -list` failed (as it did in a sandbox), validation dropped the workspace and project and validated only Swift packages, so ClockSync's app was never built. A workspace or project that cannot be read is now a failure.
- SwiftPM warns that its configuration and security directories are not writable inside a sandbox. The warning is suppressed: validation needs neither.
- Sandbox check results: the fixture, ReleaseTools (SwiftPM, remote dependencies), and ClockSync (Xcode workspace, iOS and macOS) all pass.
- Claude Code's sandbox writes to the working directory, a session temp directory, and `sandbox.filesystem.allowWrite`; Codex's workspace-write sandbox writes to the workspace, `/tmp`, `$TMPDIR`, and `sandbox_workspace_write.writable_roots`. Neither allows the two cache locations by default.
- Follow-up: the Agents repository could configure both allowances for Claude Code and Codex, so every project gets them.
- Side effect: this repository's own validation now also builds and tests the fixture package, because discovery finds it.

## `agt --version`

- Added `agt --version` using ReleaseTools' pattern: the Versionator package plugin generates `VersionatorVersion` from `git describe` at build time, and the root command prints the tag when the build is exactly a tag, otherwise the full description. The choice lives in `ToolVersion.description(tag:git:)` so it can be tested.
- Lets the `swift:validation` skill check for a release that supports agent sandboxes (3.1.0 or later) directly, instead of inferring it from failures.

## Step 3: cached discovery and `--plan`

- Measured discovery on ActionStatus (16 packages, a workspace): walking for packages 0.16 s, `swift package describe` about 1 s per package, `xcodebuild -list` 7.9 s, `-showBuildSettings` 11.9 s per scheme.
- Discovery results (package descriptions, workspace and project readability, scheme destinations) are now looked up lazily through `DiscoveryCache` in `.build/agt/discovery.json`. One fingerprint covers every package manifest, `Package.resolved`, Xcode project, workspace, and scheme (shared and user), plus the `agt` version, the selected Xcode, and the options that change discovery; any change discards the whole cache. Failed lookups are not saved. The fingerprint hashes repository-relative paths, so `/var` and `/private/var` spellings of a checkout share a cache.
- One walk now serves both package discovery and the fingerprint's file list.
- `agt validate --plan` runs discovery and lists the steps with their commands. It reuses the step runner, which lists instead of running in plan mode; steps do not depend on earlier steps' output, so the listing is exact.
- Results: ActionStatus plan 12.6 s cold, 1.0 s warm; ClockSync 5.3 s to 0.18 s; AgentTools 1.8 s to 0.17 s.
- Discovery now records each target's source path, for mapping changed files to targets in step 4.
- `--plan` makes the coverage gaps concrete: ActionStatus's full validation is three builds of one scheme (tvOS, iOS, macOS), with no tests and none of its 16 packages built or tested on their own.
